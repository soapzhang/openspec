一、简介与安装

OpenSpec Plus（opsc）是 AI 原生规范驱动开发系统，通过「先完善、再规划、后实施、可上线」的流程管理软件变更。

环境要求

依赖要求
Node.js≥ 20.19.0（ESM 模块）
包管理器pnpm
平台macOS / Linux / Windows

安装

git clone https://github.com/soapzhang/openspec.git
cd openspec
pnpm install
pnpm build              # 编译 TypeScript → dist/
npm install -g .        # 全局安装，生成 opsc 命令
opsc --version          # 验证，输出 6.0.0

开发调试可用 pnpm link 软链本地包；旧版本残留报错时先 npm rm -g openspec opsc。

二、快速开始

opsc init                   # 初始化项目（安装 9 个 Agent Skill 到 .claude/skills/）
opsc new f17085-登录重构     # 新建变更（跟踪 ID 格式）
opsc refine                 # 完善环节（spec 前强制，产出 refine.md）
opsc continue               # 输出下一个产物指令（proposal/spec/design/tasks）
opsc apply                  # 实施任务
opsc release                # 完善上线文档 release.md 并定稿（apply 后）
opsc archive                # 归档变更
opsc bug                    # 创建 bug 文档
opsc explore                # 探索模式（非强制）

三、命令总览

opsc init [path]
初始化项目，安装 9 个 Agent Skill 到 .claude/skills/
opsc new [name]
创建变更目录，命名 f<ID>-<描述>
opsc refine
强制完善环节，生成 refine.md
opsc status
查看/设置变更阶段（--set）
opsc continue
按当前阶段输出下一产物指令
opsc apply
输出实施任务指令
opsc release
完善并定稿 release.md
opsc bug
在 bugs/ 目录创建 bug 文档
opsc explore
探索模式：思考与澄清需求
opsc archive
归档变更，合并 specs 到主目录

各命令详解

opsc init — 初始化

创建目录结构 openspec++/specs|changes|archive，复制 9 个 skill 到 .claude/skills/，写 config.yaml。幂等，重复运行不覆盖已有配置。

opsc new [name] — 新建变更

命名 f<ID>-<描述>（如 f17085-登录重构）。不带名字交互引导（ID 缺省用当前日期兜底）。自动生成 .openspec.yaml（status: new）、bugs/、release.md 草稿。

opsc refine — 完善环节（强制）

spec 前必须完成，产出 refine.md。所有判断基于代码决策，完成后冻结（后续变更走 proposal/spec，不反向修改）。更新 status → refine。

opsc continue — 推进产物

按当前阶段输出下一产物的创建指令（含任务说明、依赖文件、写入位置、指导语、模板）。只读不改 status。

规模判定：refine 阶段首次 continue 时判定——交互问「复杂需求？」（默认是），非交互从 refine.md 功能细节条目数自动判定（≥3 条=large）。large 拆子能力 c1-*/c2-*/，small 四件套放变更根目录。

opsc apply — 实施

门槛：status 必须是 task。输出实施指令，按 tasks.md 逐项勾选完成。

opsc release — 上线定稿

门槛：status 必须是 cN-apply。校验 tasks 全勾完，逐节确认上线事项（DDL/DML/配置/初始化/发布服务）后置定稿。

opsc archive — 归档

校验 → 合并 specs 到主目录 → 移入 archive/<日期>-<name>/。--skip-specs 跳过合并，-y 跳过确认。

opsc bug — 记录 bug

在 bugs/b<编号>-<描述>.md 建档，编号自动递增。原因（根因分析）必填，确认后才允许改代码。

四、阶段流转

每个变更的 .openspec.yaml 记录一个 status 阶段，决定下一步做什么。

new→ refine→ proposal→ spec→ design→ task→ cN-apply
阶段含义下一步
new变更已创建opsc refine
refine完善完成opsc continue（proposal）
proposal提案完成opsc continue（specs）
spec规格完成（全子能力）opsc continue（design）
design设计完成opsc continue（tasks）
task任务清单完成opsc apply
cN-apply实施完成opsc release
阶段语义：spec/design/task 是所有子能力（cN）统一完成，不带 cN 前缀；cN-apply 是实施阶段，按子能力 1by1 推进。简单需求（无拆分）同样适用。

五、目录结构

简单需求（四件套在变更根目录）

openspec++/changes/f17085-登录重构/
├── .openspec.yaml     # 元数据（schema / size / status）
├── refine.md          # 完善环节产物（冻结）
├── release.md         # 上线文档（new 草稿，release 定稿）
├── bugs/              # bug 文档
├── proposal.md        # 提案
├── specs/             # delta 规范
│   └── <能力>/spec.md
├── design.md          # 设计文档
└── tasks.md           # 任务清单

复杂需求（spec/design/tasks 下沉到子能力）

openspec++/changes/f17085-平台重构/
├── .openspec.yaml
├── refine.md
├── release.md
├── bugs/
├── proposal.md        # 主提案（含「子能力进度」表格）
├── c1-用户权限设计/
│   ├── spec.md  design.md  tasks.md
└── c2-消息推送/
    ├── spec.md  design.md  tasks.md

归档

变更整体移入 changes/archive/YYYY-MM-DD-<name>/，release.md 原样保留为上线记录。

六、使用场景

场景一：全新项目起步

opsc init my-project
cd my-project
opsc new f17085-登录重构
opsc refine --change f17085-登录重构

场景二：推进产物（核心循环）

opsc continue --change f17085-登录重构   # 输出 proposal 指令
# ...AI 写 proposal.md...
opsc status --change f17085-登录重构 --set proposal
opsc continue                           # 输出 specs 指令
# ...AI 写 specs...
opsc status --set spec
opsc continue                           # design
opsc status --set design
opsc continue                           # tasks
opsc status --set task
约定：continue 只读不改；产物写完后用 status --set 手动推进，显式确认"写完了"。

场景三：切换 Agent 会话后恢复（重点）

切换/重启 Claude Code 会话后上下文全部丢失，恢复只需两条命令：

# 1. 看当前卡在哪个阶段
opsc status --change f17085-登录重构
#   Change: f17085-登录重构
#   阶段: design
#   下一步: opsc continue（生成 tasks）

# 2. 直接 continue，拿到下一产物指令
opsc continue --change f17085-登录重构

continue 输出完整上下文：任务说明、依赖文件路径、写入位置、instruction、模板结构。AI 照着写即可，无需回忆之前的对话。

为什么能恢复：所有进度落盘在变更目录文件 + .openspec.yaml 的 status。会话没了，状态还在。
status 显示恢复动作
newopsc refine
refineopsc continue → proposal
proposalopsc continue → specs
specopsc continue → design
designopsc continue → tasks
taskopsc apply
cN-applyopsc release

场景四：简单需求 vs 复杂需求

规模在 refine 完成后的首次 continue 时判定：

  • 简单需求（small）：proposal/specs/design/tasks 四件套直接放变更根目录，阶段照常走 spec → design → task
  • 复杂需求（large）：proposal 里拆分子能力 c1-xxx、c2-xxx，spec/design/tasks 下沉到各子能力目录

两种规模下阶段流转一致：spec/design/task 统一完成后 status --set 推进；apply 阶段复杂需求按子能力 1by1 实施。

场景五：实施与上线

opsc apply --change f17085-登录重构    # 输出实施指令（task 阶段）
# ...AI 实施，勾选 tasks.md...
opsc status --set cN-apply
opsc release --change f17085-登录重构  # 完善上线文档并定稿

场景六：归档

opsc archive f17085-登录重构
opsc archive f17085-登录重构 -y
opsc archive --skip-specs   # 纯文档变更

七、Claude Code 集成

  1. opsc init → 9 个 Agent Skill 写入 .claude/skills/（opsc-new / opsc-refine / opsc-release / opsc-continue / opsc-apply / opsc-archive / opsc-explore / opsc-bug / opsc-grill）
  2. 重启 IDE 后，Skill 按用户意图自动触发（如"新建一个变更"触发 opsc-new，skill 内部调用 opsc new）
  3. 变更目录、refine.md、release.md、bugs/ 均可在 IDE 中直接查看与编辑

八、开发本工具

pnpm install
pnpm build
node bin/opsc.js --help    # 未全局安装时用 node 直接运行
  • 语言：TypeScript（严格模式）、ESM、Node.js ≥ 20.19.0
  • CLI 框架：Commander.js；交互：@inquirer/prompts
  • 命令实现：src/clisv2/（根目录只放命令，共享逻辑在 lib/，模板在 src/template/）
